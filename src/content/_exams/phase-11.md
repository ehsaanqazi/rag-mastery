## Design problem

Meridian wants one assistant, **AskMeridian Everywhere**, serving three audiences: staff, managers and contractors. Sources are the employee handbook (HR; the 2023 version is retained for audit), about 6,000 IT runbook pages, Atlas error-code entries, and product documentation for Meridian Sync, Relay and Reports (messy PDFs and a wiki). Requirements: contractors never see employees-only content; error-code questions find the exact entry; questions that compare sources ("how does the leave policy differ from the contractor terms?") are answered from several documents; answers carry citations, with one automatic retry if a citation is invalid; retrieval p95 is 250 ms on CPU; three teams will build variants; and the Platform team has two engineers.

Choose frameworks (or none) for ingestion, retrieval orchestration and generation, and design the query path. Say where permissions are enforced, how multi-source questions are handled, how you will compare options before committing, what you would put behind your own interfaces, and how you would evaluate and keep the system upgradeable.

<details><summary>Show worked answer</summary>

**Decision method.** Decide per part, not for the whole system, and run a time-boxed bake-off on the hardest flow (permissions, the citation loop, a multi-source question) with a fixed evaluation set and fixed embedding model, store, chunks, generator and prompt, as in [framework comparisons](/learn/haystack-and-other-frameworks/framework-comparisons). Quality will probably tie, so the rubric weights reviewability and operability, with permission correctness as a pass/fail gate.

**Ingestion: LlamaIndex.** The product PDFs and wiki are messy and structured; LlamaIndex's readers, node parsers (structure-aware parsing before a size-bounded splitter, section paths in metadata) and `IngestionPipeline` with a docstore give change detection. Pin stable ids and exclude volatile metadata so hashes are stable, and give every chunk `doc_key`, `audience`, `version_status` and `content_hash`. Chunks go to the existing Qdrant collection. Re-index by key.

**Query path: Haystack.** The path has a fusion, a bounded loop and variants owned by other teams, which suits an explicit, serialisable graph. Components: a permission filter builder (from the authenticated user's groups), BM25 and dense retrievers both given the filter at run time with `FilterPolicy.MERGE`, a `DocumentJoiner` with RRF, an exact-code booster, a cross-encoder ranker over about 20 candidates, an audience check, a prompt builder, the generator, and a router that validates citations and loops back once (re-supplying documents, `max_runs_per_component=2`, with a final route that returns the answer plus a warning).

**Multi-source questions.** Do not decompose every question. Route only comparative or multi-part questions to a decomposition step (LlamaIndex's sub-question engine or a Haystack sub-pipeline per source), because it costs at least 1 + n + 1 model calls. A cheap classifier or rule decides. Simple questions skip it, and the retrieval latency budget applies only to the standard path.

**Own interfaces.** A small custom core owns the request contract: `retrieve(question, user) -> list[Passage]` and `generate(question, passages) -> Answer`, with the permission rules, the audit log of prompts and the evaluation harness in your own code. Haystack retrievers sit behind adapters; framework types stop at the adapter. The generator is a class around the Anthropic SDK, not a framework class.

**Permissions.** Built per request from identity, enforced as a filter in every retrieval branch, re-checked on the final list before the prompt builder, tested with a deliberately leaky retriever and with every user-facing filter option as a contractor; the tests are a release gate. Constructor filters are never relied on.

**Latency.** With `run_async`, BM25 (assume 10 ms) and dense (assume 40 ms) overlap; reranking 20 candidates at an assumed 4 ms is 80 ms; fusion, boosting and checks are under 1 ms. Total about 130 ms, inside 250 ms. Measure these on your hardware.

**Prompt quality over time.** Use DSPy only offline on the citation step if the golden set is large enough (a few hundred held-out questions) and re-compile on model changes; export the optimised instruction into the Haystack template. Exclude content visible to only some users from training data, because demonstrations appear in every prompt.

**Upgradeability.** Pin every framework package, run the evaluation set in CI on any upgrade, and keep upgrade-sensitive code in adapters. Record the decision, the evidence and the conditions that would change it (many more integrations, long-running agents, more teams).

**Trade-offs.** Two frameworks mean two dependency trees and two mental models, accepted because ingestion and orchestration have genuinely different needs and the boundary is the document store. With two engineers, the custom core must stay small; if that proves too costly, collapse onto one framework behind the same interfaces.

## Debugging problem

AskMeridian's support team reports four symptoms after a framework refactor. The system has a LlamaIndex ingestion pipeline writing to Qdrant, a Haystack query pipeline, and a LangChain-based Slack bot that calls a custom retriever.

1. The handbook is re-indexed nightly, but after a policy edit, answers sometimes quote the old text.
2. The Slack bot passes `user_groups` to the retriever via `retriever.invoke(question, user_groups=groups)`, and contractors occasionally see managers-only passages.
3. The Haystack pipeline with a citation retry loop sometimes returns a result with no `answer` key and logs that the prompt builder was "blocked".
4. A new "similar to the question" feature uses `similarity_score_threshold` with `score_threshold=0.3` on a FAISS store of normalised vectors and returns nothing for every query.

Give a diagnosis and a fix for each, say which two are security-relevant, and describe one test per symptom that would have caught it.

<details><summary>Show worked answer</summary>

**1. Stale chunks.** The LlamaIndex pipeline's hash covers all metadata, so volatile file metadata may make every document look changed, or, in the Haystack indexing path, edits produce chunk ids that never collide with the old ones (ids hash content, metadata and the parent's hash), so `OVERWRITE` leaves old chunks. In either path the old chunks survive because nothing deletes by a stable key. Fix: give every chunk a `doc_key`, exclude volatile metadata from hashing, re-index by key (delete the key's chunks, then write), delete by key when a source is withdrawn, and run a nightly consistency check of chunk counts per key. Test: index version 1, edit one sentence, re-index, and assert that the store holds only version 2's chunks for that key.

**2. Dropped permission context (security).** Undeclared keyword arguments to `invoke` are silently dropped by a LangChain retriever, so the permission filter is never applied. Fix: pass identity through `configurable_fields` or a per-request retriever instance, make the retriever fail closed when identity is missing (return nothing or raise), apply the filter inside the search, and add a post-retrieval audience check before the prompt. Test: call the retriever as a contractor with and without identity and assert that no managers-only passage is returned and that missing identity raises.

**3. Blocked loop.** On the retry pass the prompt builder is triggered by the router's feedback, but its mandatory `documents` input came from a retriever and was consumed on pass one; nothing re-supplies it, so it fails the mandatory-input gate, nothing else can run, and the pipeline returns partial outputs and logs the warning. It is intermittent because the loop only runs when the first answer fails the check. Fix: re-supply the documents on the loop (route the retry through the retriever entry using a `BranchJoiner`, or have the router output the documents), bound the loop with `max_runs_per_component`, give the router a default route, and handle `PipelineMaxComponentRuns`. Test: a fake generator that fails the citation check once, asserting an `answer` key and two visits to the generator.

**4. Wrong score conversion.** Relevance scores are store-specific conversions of a distance. FAISS with a flat L2 index returns squared Euclidean distance, and for unit vectors that is 2 minus twice the cosine; a default conversion that assumes plain distance produces relevance values far below the cosine, so a threshold of 0.3 rejects everything. Fix: pass the correct relevance conversion for the index, or compute cosine yourself and threshold on it, choosing the threshold on labelled data. Test: with known pairs whose cosine is 0.6, assert the retriever returns them at the chosen threshold.

**Security-relevant symptoms.** Symptom 2, a direct permission leak, and symptom 1 to the extent that stale chunks can include withdrawn or restricted content (for example the 2023 handbook or text removed for legal reasons). In both cases the fix belongs in code you own and test, not in framework defaults.

</details>
